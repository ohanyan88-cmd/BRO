# BRO — Project and Context Model v0.1

**Status:** CANONICAL DESIGN DRAFT  
**Scope:** Project BRO, isolation, inheritance, promotion, context assembly

## 1. Purpose

A Project BRO is the same BRO operating inside a governed Project boundary. It is not a clone, persona, agent, fork, or competing identity.

## 2. Ownership

| Concern | Single owner |
|---|---|
| BRO identity | SELF |
| Relationship stance | HEART |
| Project facts/policies/artifacts | Project source-of-truth |
| Project memory records | MEMORY |
| Context Manifest | NERVOUS SYSTEM |
| Context inclusion/promotion Authority Decision | IMMUNE SYSTEM |
| Project Goal/Decision/Plan | MIND |
| Project capability definitions | SKILLS & KNOWLEDGE |

## 3. Project Definition

Project record:

- `project_id` and version;
- name/purpose;
- canonical source-of-truth locations;
- owners and authority sources;
- members/roles;
- data classification;
- project policies;
- tools/integrations;
- environments/targets;
- capabilities/specialists;
- budgets/limits;
- retention/export rules;
- isolation policy;
- promotion policy;
- status and effective time;
- integrity/audit references.

## 4. Inheritance

Project BRO inherits:

- Constitution;
- active SELF;
- applicable HEART envelope;
- universal authority/security rules;
- canonical runtime contracts;
- provider-independent behavior.

Project adds only scoped facts, policies, tools, memory, capability configuration, and authority.

Project cannot amend Constitution, fork SELF, claim unrelated context, or weaken universal gates.

## 5. Isolation Boundary

Isolation applies to:

- facts and documents;
- memory;
- context retrieval;
- tools/credentials;
- artifacts;
- tasks/events/evidence;
- specialists;
- budgets;
- logs/audit visibility;
- learning/promotion;
- exports.

Every access binds project ID, principal, purpose, Task, sensitivity, operation, and Authority Decision.

## 6. Project Source-of-Truth

Project source-of-truth owns current Project facts and policies. MEMORY stores governed continuity and pointers, not competing copies.

Each source declares:

- authority;
- scope;
- version/effective time;
- format/location;
- freshness;
- conflict/supersession rules;
- integrity;
- access classification.

If current source conflicts with credible prior context, the conflict remains visible until authority/version evidence resolves it.

## 7. Context Manifest

NERVOUS SYSTEM owns each immutable manifest revision.

Fields:

- Task/Goal/Decision purpose;
- active SELF/HEART refs;
- Project ID and source versions;
- included Observations/memory/capabilities/policies;
- authority/sensitivity/freshness/trust per reference;
- exclusions and reason where material;
- conflicts/quarantine;
- token/resource budget;
- creation time/version/integrity;
- expiry/reassembly triggers.

## 8. Assembly Pipeline

1. establish Task/Goal and Project boundary;
2. verify principal/project authority;
3. activate minimal SELF/HEART;
4. load current project truth needed for the decision;
5. retrieve scoped Project/Work/Decision memory;
6. collect required current Observations;
7. load capability/tool/authority state;
8. detect conflict, staleness, sensitivity, injection, and quarantine;
9. apply relevance/materiality ranking;
10. enforce least-context and budgets;
11. record manifest and exclusions;
12. reassemble on material change.

## 9. Context Precedence

Context relevance does not equal authority.

For Project facts:

- current verified project source governs;
- current direct Observation may reveal source staleness/conflict;
- prior Decision Memory acts as contradiction detector;
- general user memory cannot silently override Project truth;
- specialist/model output is a proposal or observation, not authority.

## 10. Cross-Project Sharing

Default is deny.

Sharing requires:

- source Project authorization;
- destination Project authorization;
- exact data/classification;
- purpose;
- minimization/redaction;
- sensitivity/privacy controls;
- retention/expiry;
- provenance;
- audit;
- revocation/withdrawal behavior.

Raw private relationship foundation and secrets are never promoted as reusable project knowledge.

## 11. Learning Promotion

Learning stays in its source scope until promotion.

Promotion classes:

- Work → Project;
- Project → User/general reusable context;
- Project → Capability/Skill;
- Failure → prevention control;
- Evidence → Evidence Reference Memory.

Promotion requires generalization, removal of unnecessary private/project specifics, evidence, target-owner acceptance, and Authority Decision.

## 12. Project Lifecycle

States:

- `DRAFT`;
- `ACTIVE`;
- `PAUSED`;
- `ARCHIVING`;
- `ARCHIVED`;
- `QUARANTINED`;
- `CLOSED`.

Archive/close must define active Task handling, tool revocation, memory retention, artifact custody, export, audit preservation, and reactivation authority.

## 13. Multi-Project Runtime

- each Task has exactly one primary Project boundary or explicit global scope;
- cross-project work uses a governed composite manifest, not silent merging;
- specialists receive only assignment/project context;
- identical tools use distinct project credentials/scopes;
- shared mutable targets require explicit ownership/conflict controls;
- user interaction remains one BRO even when multiple project contexts contribute.

## 14. Target Repository Decision

The sole Project source-of-truth and implementation repository for this BRO build is:

`https://github.com/ohanyan88-cmd/BRO`

`menqstudio/OS` is a read-only donor/reference repository. No target state is written there. Selected code enters BRO only through a recorded selective-port process.

## 15. Acceptance Gates

- PC-1: Project BRO never forks identity.
- PC-2: every Task has explicit Project/global scope.
- PC-3: project data cannot leak through retrieval, delegation, logs, or learning.
- PC-4: Context Manifest is reproducible from referenced versions.
- PC-5: current source conflicts remain visible.
- PC-6: cross-project sharing defaults deny.
- PC-7: promotion is minimized, evidenced, authorized, and auditable.
- PC-8: archive/close revokes tools and preserves required evidence.
- PC-9: model/provider change cannot bypass isolation.
- PC-10: `ohanyan88-cmd/BRO` is the only target implementation SOT.
- PC-11: OS donor remains unmodified.
- PC-12: multi-project work still communicates as one BRO.

## 16. Decision

Project BRO is a scoped operating embodiment of the same BRO. Project context is powerful but bounded: inherited identity, isolated truth, minimal context, explicit authority, and governed learning.

> **One BRO across projects. One boundary per task. No silent leakage. No identity forks.**
